# 찬양 중 잘못된 언어 출력 조사

2026-11-09의 **1차 조사 기록**입니다. 저장 로그와 문서·SDK를 조사하고, 승인된 US$5 미만 범위에서 Live Translate 재생 비교를 수행했습니다. 기준 재생에서 베트남어가 재현됐고, 언어 힌트만 추가한 3회 모두 같은 문제가 계속됐습니다. 당시 잠정 권고는 C였습니다.

이후 별도 승인된 [문맥 유지 후속 시험](/docs/reconnect_context_experiments.md)에서 프라이밍과 세션 재개가 각각 3회 모두 이탈을 예방해 B1을 권고했습니다. 구현 후 [전체 예배 검증](/docs/b1_full_service_validation.md)에서는 긴 첫 찬양의 이탈이 나타나지 않았지만 송영의 일본어 오인식이 남았습니다. 아래 표와 제품 미변경 설명은 1차 조사 당시 기록이며 언어 힌트의 부정적 결과는 그대로 유효합니다.

제품 코드·설정·EXE는 바꾸지 않았고 숨김·음소거 필터도 복원하지 않았습니다. 조사용 스크립트와 원시 결과는 `/.agent/archive/2026-11-09-song-drift/`에만 보관합니다. 보호 대상으로 해시를 기록한 제품 파일 45개가 모두 그대로입니다.

## A. 같은 음원으로 수행한 유료 비교

### 음원과 시간 대응

- 원본: `/.agent/sessions/20261108_121729/ground_truth/2026_11_8_recording.mp3`, 약 90분 15초.
- 잘라낸 범위: 녹음 **00:22:46~00:27:56**, 310초. 스테레오를 L/R 각각 0.5로 평균한 뒤 16 kHz 모노 PCM16으로 변환했습니다. 모든 재생에 같은 PCM을 사용했습니다.
- PCM SHA-256: `679b707908e7220a89e006a43ad0812fb7c483d656f54ceffe0b055678f50969`.
- 앞선 검증의 `녹음 위치 ≈ 서비스 경과 시간 + 825초` 대응을 사용했습니다. 원래 연결은 11:09:15.879, 첫 베트남어는 11:09:18.381, 한국어 복귀는 11:13:56.145입니다. 예상 녹음 위치는 각각 약 22:46, 22:49, 27:27입니다.
- ChatGPT 참조 전사본의 22:52~26:52 항목은 찬양이며, 27:32 항목은 사도신경입니다. 재생 결과도 같은 순서로 돌아와 구간 선택을 뒷받침합니다. 단어 시각을 사람이 검수한 동기화 결과는 아닙니다.

공급된 녹음은 당시 수신기·마이크에서 서버가 받은 원본 PCM이 아닙니다. 모노/스테레오 전환이나 당시 입력의 모든 특성을 재현했다고 주장하지 않습니다. 참조 전사본도 사람의 확정 정답은 아닙니다.

### 실행 조건과 결과

모델은 `gemini-3.5-live-translate-preview`, SDK는 2.33.0입니다. 현재 제품의 `_build_config()`를 사용했습니다. 출력 영어, Orus, `echo_target_language=True`, VAD와 sliding window를 유지하고 100ms씩 실제 속도로 보냈습니다. 매번 새 연결을 열었으며 자동 재연결·재시도는 하지 않았습니다. 힌트군에서는 입력 전사 설정의 `language_codes=["ko", "en"]`만 달랐습니다.

기준 1회에서 재현됐으므로 기준을 더 반복하지 않고 힌트 비교 3회로 진행했습니다. 아래 시각은 각 재생 시작 이후의 **수신 시각**이며 실제 발화 시각과 동일하지 않습니다.

영어 전사에도 참조 찬양에 없는 어머니·질병 등에 관한 서술이 나타났습니다. 언어 코드 표시만 틀린 것으로 축소하지 않습니다. 다만 실제 합성 음성을 사람이 청취·채점하거나 전체 예배의 번역 정확도를 평가한 시험은 아닙니다.

이번 Live Translate 응답은 `turn_complete`를 보내지 않았습니다. 따라서 API가 확정한 턴별 통계로 임의 분할하지 않았습니다. 원시 JSON에 모든 코드·텍스트 수신 시각을 보관했고, 표의 횟수는 발화 수가 아닌 **언어 코드가 붙은 수신 이벤트 수**입니다. 각 실행의 미종료 스트림도 `complete: false`로 남겼습니다.

### 비용과 중단 범위

총 유료 연결은 **4회**, 보낸 음원은 **1,240초(20분 40초)**입니다. 응답에서 보고한 입력 토큰 합계는 30,900, 출력 토큰 합계는 30,900입니다. 입력 US$3.50/백만 토큰, 출력 US$21.00/백만 토큰으로 계산한 합계는 **US$0.757050**, 약 **US$0.76**입니다. [Google 공식 요금](https://ai.google.dev/gemini-api/docs/pricing).

이는 API 사용량에 따른 추정이며 청구서 확인 금액이 아닙니다. 사용량 이벤트를 중복 제거하지 않고 합산해 보수적으로 기록했습니다. 낮은 중단 기준과 최대 턴 비용 여유를 두었으며, 승인된 US$5 한도에 도달하지 않았습니다. 요청한 비교를 마친 뒤 추가 호출하지 않았습니다.

### B1. 세션 재개 지원과 새 연결을 사용하는 이유

Google의 일반 Live API 참조는 `sessionResumption`을 설정하면 `SessionResumptionUpdate`를 보내고, 이후 연결에 핸들을 전달해 재개하는 장치를 설명합니다. 설치된 SDK 2.33.0에도 `SessionResumptionConfig(handle, transparent)`와 `LiveServerSessionResumptionUpdate(new_handle, resumable, last_consumed_client_message_index)`가 있습니다. 재개 설정의 직렬화도 로컬에서 확인했습니다. [공식 Live API 참조](https://ai.google.dev/api/live), [공식 SDK](https://github.com/googleapis/python-genai).

이것만으로 **현재 번역 모델의 서버가 이 예배에서 안정적으로 재개하며 언어 이탈을 막는다고 보장할 수는 없습니다.** 번역 전용 가이드는 재개에 관해 모델별 보장을 명시하지 않습니다. 이번에는 요청대로 문서·SDK만 확인했고 모델의 실제 핸들 발급·재접속 시험은 하지 않았습니다. 따라서 지원되지 않는다고 단정하는 것도, 검증된 해결책이라고 말하는 것도 근거가 부족합니다. [Live Translate 가이드](https://ai.google.dev/gemini-api/docs/live-api/live-translate).

현재 코드의 새 연결은 의도된 선택입니다. 보관된 `v3.3.0` 기준 커밋 `aa469dd`의 코드 주석은 9분 주기 GoAway에서 문맥 누적과 번역 이탈을 피하려고 재개 설정을 생략하고 핸들 업데이트를 무시한다고 적었습니다. 조사한 기간의 중복 제거 로그에서도 `resumption_handle_present`가 기록된 **300개 메시지는 모두 False**였습니다. 이는 당시 앱이 핸들을 보내지 않았다는 근거이며 서버의 미지원 증거는 아닙니다.

이전 개인 인계문에는 `handle` 대신 `new_handle`·`resumable`을 읽도록 고치는 커밋 메시지 초안도 있습니다. 초안은 실제 배포·성공 시험 기록으로 취급하지 않았습니다. 별도의 다중 모드 번역 앱도 재개 후 이전 번역이 반복되는 문제를 보고하지만, 그 앱의 결과를 이 예배나 현재 번역 모델만의 실측으로 대체하지 않습니다. [외부 구현의 재연결·재개 경험](https://github.com/kazunori279/live-translator).
